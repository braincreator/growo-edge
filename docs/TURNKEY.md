# Плейбук: проект под ключ на Growo Edge SDK

Модель: **платформа Growo — SaaS (наша), проект клиента — форк этого репо
(передаваемый)**. В форке живёт только «клей»: адаптеры каналов, вебхуки,
скрипты загрузки данных. Поведение ассистента (промпты, RAG, скоринг,
база знаний) настраивается в платформе и в исходники клиента не попадает.

## Сценарии

### А. Всё из коробки — код не передаётся
Клиенту нужны сайт-виджет + amoCRM + база знаний:
1. Тенант + тариф в платформе; визард клиента (база знаний, тон).
2. Виджет на сайт — одна строка кода (даём в платформе).
3. amoCRM: привязка аккаунта (платформа) + ZIP amo-виджета (вход из amo).
4. Edge SDK не нужен.

### Б. Кастомный клей — форк этого репо
Нужен канал/правила, которых нет в платформе:
```bash
git clone <этот репо> growo-client-<имя>
cd growo-client-<имя>
git remote set-url origin <репо проекта>
cp .env.example .env    # GROWO_TENANT, GROWO_API_KEY (admin_token), креды
pip install -e ".[dev]" # локальная разработка
pytest                  # должен быть зелёным до начал правок
docker compose up -d    # деплой приёмника (у клиента или на VPS)
```

Типовые доработки (все — в `examples/`):
- **Авито-бот**: `avito_bot.py` + однократно `register_avito_webhook.py`
  (PUBLIC_URL = публичный адрес приёмника). Кастомные правила (расписание,
  фильтры товаров, человеко-часы) — правьте `reply()` и парсинг.
- **Лиды из любых форм в amoCRM**: `amo_push_lead.py` — боевой паттерн
  контакт(дедуп)→сделка→примечание→задача.
- **Массовая загрузка базы знаний**: `kb_upload.py ./docs/*` — документы
  сразу с эмбеддингами (семантический поиск ассистента видит их сразу).

### В. Поддержка после сдачи
Клиент нанимает подрядчика → доступ к репо форка. Подрядчик правит клей;
платформа и её поведение остаются на API Growo.

## Правило «что где решается»

| Потребность | Где решается |
|---|---|
| Ассистент знает новые условия/акции | База знаний платформы (не код) |
| Тон, сценарии, скоринг лидов | Админка платформы (не код) |
| Новый канал, свои правила вебхука | Форк SDK (код) |
| Интеграция с системами клиента | Форк SDK (код) |

## Контрольный список внедрения

1. [ ] Тенант + план; `admin_token` выдан (это `GROWO_API_KEY` в .env)
2. [ ] Форк создан, тесты зелёные, `.env` заполнен
3. [ ] База знаний загружена; проверка: вопрос ассистенту — отвечает по докам
4. [ ] Каналы: вебхук зарегистрирован, ответ ассистента возвращается в канал
5. [ ] amo: аккаунт привязан, лид из чата появляется сделкой
6. [ ] Хендовер: доступ к репо + этот файл + договор на платформу

## Ограничения (честно)

- `GROWO_API_KEY` = admin-токен тенанта: даёт управление тенантом. Не
  публикуйте его во фронтенде — только серверная сторона (edge-приёмник,
  скрипты). Ролевые ключи (операторские) — в дорожной карте платформы.
- Чат-эндпоинт без Origin-гейта авторизуется слагом тенанта: слаг + домен
  виджета не секрет, секрет — admin-токен.
- Авито-токен короткоживущий (~24ч): клиент обновляет автоматически
  (client_credentials), но креды — только в `.env`, не в код.

## Жизненный цикл: edge → платформа

Edge SDK — быстрый контур продукта. Клей из клиентских форков вливается в
платформу **выборочно и через переписывание**, не копипастом:

```
внедрение (форк, дни) → паттерн повторился у 2–3 клиентов
  → продуктовая фича платформы (коннектор/модуль/настройка в админке)
  → следующий клиент этого типа — из коробки, ноль кода
```

Правила:
- В платформу уходит **повторяемое** (каналы, расписания, интеграции,
  нужные любому). Клиентоспецифичный клей остаётся в его форке навсегда.
- Вливание = переписывание в коннекторный каркас платформы (транспорт,
  Vault-креды, capabilities, автодиспетчер, атрибуция). SDK-клиент и
  платформенный коннектор живут параллельно: лёгкий для edge-случаев,
  полный для SaaS.
- Сигнал к вливанию: одна и та же доработка сделана во 2-м форке —
  значит это продуктовая фича, а не клей.
